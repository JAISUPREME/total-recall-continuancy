# Total Recall Continuancy Framework

Total Recall Continuancy is a human-governed method for carrying project and research state across chats, models, providers, and time without treating any AI session as sovereign memory.

The durable substrate is the user-controlled repository. Chats, model outputs, exports, summaries, and platform memories are evidence or labor layers around that substrate. A fresh model re-enters through a master/state/provenance/resume package, demonstrates that it understood the package, and only then continues work.

## Core law

The model is not the archive.

The chat is not the archive.

The provider is not the archive.

The approved user-controlled state is the continuity object.

## What problem this solves

Long AI chats degrade.

Old chats become hard to navigate.

Fresh chats lose nuance.

Platform memory is useful, but it is not the same thing as user-governed project state.

Raw conversation exports preserve text, but they do not automatically identify current state, superseded decisions, open questions, authority, evidence quality, or the correct resume point.

Continuancy solves this by making the continuity object explicit, portable, inspectable, versioned, and human-governed.

## Governing laws

### Local State Law

The user-controlled repository is the durable memory substrate.

### Model Non-Sovereignty Law

A model may extract, organize, reason, or retrieve. It does not own current truth.

### Clone-Forward Law

Never patch or overwrite an approved historical artifact. Clone, version, relate, and move forward.

### Provenance Law

A conclusion without a path back to its source is not a complete research object.

### Export Does Not Equal Continuity Law

A provider export is source material, not automatically reconstructed state.

### Source-Grounded Memory Law

Frozen source evidence remains separate from mutable or derived model memory.

### Human Authority Law

Approval, correction, and current-state selection remain explicit human gates.

### Re-Entry Law

Continuation begins only after the receiver demonstrates correct understanding of state, boundaries, and resume point.

### Unknown Law

Missing information remains UNKNOWN. It is not silently reconstructed.

### Bounded Retrieval Law

A new chat receives only the deeper source or artifact branches needed for the current task. No giant blind context dump is required.

## End-to-end operating chain

Search / Source → Capture → Tag → Analyze → Create → Register → Relate / Version → Validate → Master → Human Review → Handoff Acceptance → Continuation

### Search / Source

Identify the actual external, attached, local, or prior artifact being used.

### Capture

Preserve bibliographic identity, exact locator or selector, and appropriate local or archived representation.

### Tag

Assign topic, lane, entities, artifact type, evidence status, version, relationships, and current status.

### Analyze

Separate facts, testimony, inference, user thesis, speculation, dispute, UNKNOWN, and audit gaps.

### Create

Freeze meaningful branches into durable artifacts instead of leaving them only in transient chat.

### Register

Log exact filename, role, origin, status, relationships, preservation level, and fingerprint if frozen.

### Relate / Version

Declare lineage: BUILDS_ON, CORRECTS, SUPERSEDES, CITES, VERIFIES, DERIVED_FROM, BRANCHES_FROM, MERGES_WITH, or REJECTS.

### Validate

Check package completeness, source anchors, and fixity according to profile. Integrity validation does not prove factual truth.

### Master

Assemble continuity state from accumulated records, not from model recollection.

### Human Review

Human review determines current, approved, provisional, rejected, superseded, held, UNKNOWN, and do-not-infer state.

### Handoff Acceptance

The fresh receiver demonstrates understanding before meaningful continuation.

### Continuation

New work proceeds from approved state and preserves the same chain going forward.

## System layers

### Raw History

Chats, exports, transcripts, screenshots, and source files. Historical evidence, not automatically current truth.

### Preserved Artifacts

Research notes, reports, images, code, packages, source captures, local copies, and other durable work products.

### Provenance / Relationships

Explicit lineage among claims, sources, decisions, corrections, versions, artifacts, and chats.

### Approved State

Human-governed current truth: approved, provisional, superseded, rejected, held, UNKNOWN, and do-not-infer.

### Start Here / Master

Human-readable map of current state plus paths to deeper evidence.

### Re-Entry Validation

Fresh chat demonstrates correct understanding before continuing.

### Continuation

New work proceeds from accepted handoff and creates new lineage.

### Historical Witness

A prior chat may answer one bounded historical clarification from preserved context. It does not govern present state.

## Multi-chat lineage

CHAT A → MASTER A → CHAT B → MASTER B → CHAT C → MASTER C

Chat A creates research, decisions, corrections, sources, and artifacts. Its master records current state and lineage at closeout.

Chat B starts by reading START HERE, Master A, and the current state or artifact register. It proves re-entry before continuing.

Chat B creates new artifacts and may reference selected evidence from Chat A. Master B BUILDS_ON Master A and records what changed.

Chat C does not need Chat A loaded wholesale. It starts from Master B, which points backward to Master A and to only the deeper artifacts required.

If Chat C encounters a genuine historical ambiguity that Master B cannot resolve, it may generate one bounded clarification request to Chat B or Chat A if the older chat uniquely retains the needed context.

The local repository remains authoritative even if Chat A or Chat B disappears from the provider interface.

## Historical witness rule

A prior chat is a witness, not a ruler.

Its valid role is to answer a narrow historical question from the context it could actually see when that question cannot be resolved from the current approved package.

Rules:

- Ask only one genuine ambiguity at a time.
- Do not ask an old chat to verify new present-tense events.
- Do not ask for a full history dump when a bounded answer is sufficient.
- Do not let the old chat silently promote an old state over the current approved master.
- Preserve the clarification as a new artifact or event with source identity and relationship to the current master.
- Human review remains the gate before the clarification changes current state.

## Continuation Acceptance Test V1

Before continuing substantive work, the receiving chat must answer:

1. Current state — State the current approved state without importing superseded or historical-only claims.
2. Authority — Identify who governs approval/correction and what the model is authorized to do now.
3. Active artifacts — Identify the current master/framework/research artifacts and distinguish them from superseded ancestors.
4. Evidence boundaries — Identify what is established, inferred, user thesis, speculative, disputed, or UNKNOWN.
5. Do-not-infer — Repeat the material boundaries that must not be silently filled or reconstructed.
6. Resume point — State exactly where work stopped and the next permissible continuation action.
7. Ambiguity test — Identify any one genuine ambiguity that blocks correct continuation. If none exists, say so explicitly.

## PASS / FAIL / clarification rules

PASS: The fresh chat’s answers agree with the approved master/state, preserve UNKNOWN items, respect authority, and distinguish current from superseded artifacts.

FAIL: Any conflict, resurrection of superseded state, invented fact, authority drift, or unresolved material ambiguity blocks continuation.

CLARIFICATION: One historical ambiguity may produce exactly one bounded request to the relevant prior chat or source artifact.

REVIEW: The answer from the prior chat or source does not automatically become current truth. It is reviewed and then incorporated through a new state transition if accepted.

CONTINUE: Only after acceptance does the fresh chat resume substantive work.

## Four-part continuation minimum

MASTER + STATE + PROVENANCE + RESUME

## Artifact and download linking law

Every meaningful downloadable artifact created or attached in a chat gets an artifact-register entry.

Each entry records exact filename, created or received time where available, role, artifact class, status, relationships, and preservation or fixity note.

The master points to exact filenames so a user can locate the file in Downloads or local storage and provide it to a new chat without guessing.

Important research documents carry their own source register so they remain intelligible if separated from the chat.

Links are useful retrieval paths, but filename and bibliographic/source identity must survive independently of those links.

The relationship map tells the next chat which files are current, superseded, supporting, derived, verifying, or historical.

## Evidence classes

### Source Record

Preserved evidence object. Immutable once frozen except through a new version or capture.

### Derived Record

Summary, extraction, model synthesis, profile, claim, or memory derived from one or more sources.

### Current State Record

Human-approved pointer to what currently governs action.

### User Thesis

User-proposed interpretation or working theory. Preserved as such unless independently established.

### Structural Inference

Reasoned synthesis that is not itself a directly observed fact.

### Speculative Branch

Possible explanation retained for inquiry but not promoted into current truth.

### UNKNOWN / Audit Gap

Information not established or not independently auditable from available material.

## Failure behavior

Dead URL: Retain bibliographic identity; use archived or local capture when available.

Source page changed: Create new capture/version and retain the predecessor.

Wrong summary promoted to memory: Return to source-grounded record; correct derived state through explicit transition.

Two masters conflict: Human-approved current-state pointer resolves present authority; both remain preserved.

Superseded file resurfaces: Status/relationship graph prevents silent promotion.

Raw provider export imported: Normalize as source/history; never assume current truth or rehydrated continuity.

Handoff not understood: Stop at acceptance/clarification gate; do not continue by inference.

Old chat unavailable: Continue from local approved state; old-chat witness is optional, not a dependency.

Artifact missing: Mark missing or unavailable; do not invent its contents.

## Profiles

### BASIC

Personal/chat continuity: START HERE, master/state, key artifacts, resume.

### RESEARCH

Adds bibliography, exact source selectors, claims ledger, and captured evidence.

### PROJECT

Adds decisions, artifact lineage, statuses, version/release manifests.

### ARCHIVAL

Adds preservation events, full fixity, durable captures, package validation, and stronger metadata.

A profile changes depth, not authority. Human governance and re-entry rules do not weaken in lighter profiles.

## What this framework does not claim

This framework does not claim:

- That no one else has components of this architecture.
- That this is the only valid continuity design.
- That old chats are permanently available, infallible, or authoritative over current state.
- That a fresh model has consciousness, identity, or subjective continuity because state can be rehydrated.
- That every artifact must be loaded into every new chat.
- That cryptographic integrity proves factual truth.
- That any current provider export fully reconstructs original model/session state.
- That historical ancestors may be silently rewritten.

Preserve the source. Preserve the artifact. Preserve the relationship. Preserve the correction. Prove re-entry. Then continue.
